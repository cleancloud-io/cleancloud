aws.ebs.snapshot.old - Canonical Rule Specification

Intent
Detect self-owned EBS snapshots that are old enough to be cleanup review candidates
after excluding strong AWS-documented blockers and high-confidence dependency signals.

This is a read-only hygiene rule. It is not a delete-safe rule, not an idle-usage rule,
and not proof that a snapshot is unused or safe to remove.


1. AWS API grounding

This specification is anchored to official EC2/EBS API and user-guide behavior.

AWS facts relied on
- DescribeSnapshots with OwnerIds=["self"] returns self-owned snapshots only.
- AWS strongly recommends paginated DescribeSnapshots requests.
- Snapshot fields returned by DescribeSnapshots include:
  - snapshotId
  - startTime
  - status
  - storageTier
  - volumeId
  - volumeSize
  - fullSnapshotSizeInBytes
  - description
  - dataEncryptionKeyId
  - tags
- Snapshot status can be:
  - pending
  - completed
  - error
  - recoverable
  - recovering
- storageTier can be:
  - standard
  - archive
- EBS snapshots are incremental after the first snapshot.
- fullSnapshotSizeInBytes is NOT the incremental size and is NOT billed monthly size.
- Deleting a snapshot might not reduce storage cost because later snapshots can still
  reference its data.
- You can't delete snapshots associated with registered AMIs; AWS deletion guidance
  specifically calls out registered/disabled AMI linkage as a blocker.
- If you delete a shared snapshot that you own, accounts it is shared with lose access.
- DescribeSnapshotAttribute(Attribute="createVolumePermission") can reveal public or
  cross-account create-volume sharing.
- DescribeImages supports filter block-device-mapping.snapshot-id and strongly
  recommends pagination.
- Archived snapshots have different pricing/behavior, and archive tier has a minimum
  90-day archive period with early-delete considerations.

Rule-design consequence
- Age alone is not a delete signal.
- This rule must be a conservative review-candidate detector, not a waste-truth detector.
- Numeric monthly cost must not be derived from volumeSize.
- AWS Backup-managed snapshots are a false-positive risk unless explicitly excluded or
  treated as unknown and skipped.


2. Scope

Included
- snapshots returned by DescribeSnapshots with OwnerIds=["self"]
- snapshots in status == "completed"
- snapshots in storageTier == "standard"
- snapshots older than max_age_days after required blocker checks pass

Excluded
- non-self-owned snapshots
- snapshots not in completed state
- archived snapshots
- malformed snapshot records without snapshotId or startTime
- snapshots linked to self-owned AMIs
- snapshots with public or explicit external create-volume permissions
- snapshots that are explicitly identified as AWS Backup-managed
- snapshots for which required blocker visibility is unavailable


3. Canonical definitions

age_days
- Days since startTime.

max_age_days
- Recommended default: 90
- This is a product-policy threshold, not an AWS-defined cleanup signal.

ami_linked
- True when DescribeImages for self-owned images finds block-device-mapping.snapshot-id
  reference(s) to the snapshot.
- Scope is self-owned AMIs only.
- Cross-account AMI usage risk is indirectly reduced by the external-sharing blocker.

shared_externally
- True when DescribeSnapshotAttribute(createVolumePermission) shows:
  - group == "all", or
  - a user/account permission outside the owner account context

backup_managed
- True when explicit product heuristics indicate the snapshot is managed by AWS Backup.
- Until AWS Backup integration is added, this should be treated conservatively:
  explicit Backup-managed evidence may exclude; lack of evidence is not proof of
  non-Backup ownership.
- backup_managed == unknown does not block detection by itself.
- Only explicit backup_managed == true is an exclusion signal in the current spec.

full_snapshot_size_bytes
- The full size of blocks written at snapshot creation time.
- This is not incremental billed size and not a monthly cost metric.


4. Signal model

This rule uses three signal buckets.

A. EXCLUSION_RULES
These suppress findings.

1. status != completed
   -> SKIP

2. storageTier != standard
   -> SKIP

3. age_days < max_age_days
   -> SKIP

4. ami_linked == true
   -> SKIP

5. shared_externally == true
   -> SKIP

6. backup_managed == true
   -> SKIP

B. DETECTION_SIGNAL
This is the only finding trigger.

1. Self-owned snapshot is:
   - completed
   - standard tier
   - older than max_age_days
   - not linked to a self-owned AMI
   - not shared publicly or to other accounts
   - not explicitly identified as AWS Backup-managed

C. CONTEXTUAL_SIGNALS
These must not create findings by themselves.

Contextual signals may only:
- appear in evidence/details
- influence risk if product policy later adds explicit urgency tiers

Contextual signals include:
- description
- tags
- volumeId
- volumeSize
- fullSnapshotSizeInBytes
- dataEncryptionKeyId
- encrypted / kmsKeyId

Hard rules
- volumeSize must not be used as billed monthly cost.
- fullSnapshotSizeInBytes must not be used as billed monthly cost.
- Contextual signals must not convert age into delete-safe certainty.


5. Evaluation order (mandatory)

All implementations must follow this order:
1. Parse and normalize snapshot fields
2. Apply core scope filters (owner/self, required identifiers, status, storage tier)
3. Compute age_days
4. Apply age threshold
5. Check AMI linkage
6. Check external sharing
7. Check explicit AWS Backup-managed exclusion heuristics, if implemented
8. Emit review-candidate finding only if all exclusion checks pass
9. Assign confidence
10. Assign risk
11. Build evidence/details


6. Path logic

This rule has one detection path only.

Path: old-snapshot-review-candidate
If:
- snapshotId exists
- startTime exists
- status == completed
- storageTier == standard
- age_days >= max_age_days
- ami_linked == false
- shared_externally == false
- not explicitly identified as AWS Backup-managed

Then:
- MAY emit a finding

If any exclusion rule matches:
- MUST skip


7. Confidence model

Confidence measures strength of "cleanup review candidate" evidence, not deletion safety.

LOW
- default and recommended confidence
- reason: AWS APIs do not prove business intent, DR intent, AWS Backup ownership, or
  application/workflow dependency from age alone

MEDIUM
- optional only if future spec revisions add stronger corroborating signals beyond age
  and hard-blocker exclusions

Mandatory rule
- Current spec should use LOW confidence by default for emitted findings.


8. Risk model

Risk measures urgency, not certainty.

Recommended default
- LOW

Optional future product policy
- MEDIUM may be used if explicit urgency signals are added later, but not from
  volumeSize/fullSnapshotSizeInBytes cost assumptions alone.

Mandatory rule
- Do not infer HIGH or MEDIUM risk from age alone.


9. Cost model

Cost is informational only, and current spec recommends omitting numeric monthly cost.

Mandatory rules
- Cost must not influence:
  - detection
  - confidence
  - risk
- The rule must not estimate monthly cost from:
  - volumeSize
  - fullSnapshotSizeInBytes
- The rule must clearly disclose that EBS snapshot billing is incremental and deletion
  might not reduce cost.

Allowed behavior
- Show non-billing size context such as:
  - volumeSize
  - fullSnapshotSizeInBytes
  but only with explicit caveats


10. Failure behavior

Required API
- ec2:DescribeSnapshots
- If unavailable, the rule fails

Best-effort blocker checks
- ec2:DescribeImages
- ec2:DescribeSnapshotAttribute
- DescribeSnapshotAttribute can itself be permission-restricted; this is part of the
  blocker-visibility model and must not be treated optimistically.

Mandatory API usage rules
- Implementations MUST paginate DescribeSnapshots.
- Implementations MUST paginate DescribeImages if used for blocker checks.
- Implementations should not enumerate or reason over the full snapshot status enum;
  they only need to require status == completed for eligibility.

Conservative behavior
- If AMI linkage cannot be checked, do not emit a finding.
- If external sharing cannot be checked, do not emit a finding.
- If encrypted-snapshot permissions or other access constraints prevent blocker checks,
  do not emit a finding.
- Prefer SKIP over emission when blocker visibility is missing.

General rule
- This rule is conservative by design; missing blocker checks must not be treated as
  "no blockers found".


11. Blind spots

Every emitted finding must disclose that the rule does not prove:
- business/application retention intent
- disaster recovery intent
- manual operational workflows
- AWS Backup management, unless Backup integration is explicitly added
- whether deleting the snapshot will reduce billed storage cost
- whether the snapshot is part of a multi-volume consistency workflow

The rule should also disclose:
- later snapshots may reference data blocks from this snapshot
- archived snapshots are out of scope, including temporarily restored archived snapshots


12. Evidence contract

Every finding must include:
- evaluation_path: old-snapshot-review-candidate
- snapshot_id
- start_time
- age_days
- status
- storage_tier
- ami_linked_check result
- create_volume_permission_check result
- backup_managed_check result (true | false | unknown)
- volume_id or null
- volume_size_gib or null
- full_snapshot_size_bytes or null

signals_not_checked is optional and should be included only when relevant gaps or
blind spots need to be disclosed.

Suggested signals_not_checked content, as applicable:
1. AWS Backup management not checked
2. disaster recovery / operational retention intent
3. application-level restore workflow dependency
4. multi-volume snapshot set handling
5. cost reduction after deletion is not guaranteed

Details contract
- Missing fields must be explicit null values, not omitted.


13. Title and reason contract

Title
- Old EBS snapshot review candidate

Reason
- Snapshot exceeds age threshold and no AMI linkage, external sharing, or explicit
  AWS Backup-managed signal was found

Hard rules
- Do not call the snapshot "unused".
- Do not call the snapshot "safe to delete".
- Do not imply cost savings are guaranteed.


14. API and IAM contract

Required
- ec2:DescribeSnapshots

Best-effort blocker checks
- ec2:DescribeImages
- ec2:DescribeSnapshotAttribute

Optional future enrichment
- AWS Backup APIs, if the rule is extended to verify backup-managed snapshots

API usage constraints
- DescribeSnapshots must use OwnerIds=["self"].
- DescribeImages must restrict to self-owned images for AMI blocker checks.


15. Acceptance scenarios

Must emit
1. self-owned completed standard-tier snapshot older than threshold with:
   - no self-owned AMI linkage found
   - no external create-volume permissions found
   - no explicit AWS Backup-managed signal found

Must skip
1. snapshot younger than threshold
2. snapshot in pending/error/recoverable/recovering state
3. archived snapshot
4. snapshot linked to a self-owned AMI
5. snapshot shared publicly or to other accounts
6. snapshot explicitly identified as AWS Backup-managed
7. malformed snapshot without snapshotId
8. malformed snapshot without startTime
9. blocker checks unavailable

Must not happen
1. volumeSize is used as monthly cost
2. fullSnapshotSizeInBytes is used as monthly cost
3. AMI-linked snapshots are emitted
4. publicly/shared snapshots are emitted
5. archived snapshots are emitted
6. missing blocker visibility is treated as "no blockers"
7. explicit AWS Backup-managed snapshots are emitted


16. Short in-file contract

Suggested header for ebs_snapshot_old.py:

"""
Rule: aws.ebs.snapshot.old

Intent:
    Detect old self-owned EBS snapshots that are conservative cleanup review candidates.

Exclusions:
    - status is not completed
    - storage tier is not standard
    - snapshot is linked to a self-owned AMI
    - snapshot is shared publicly or to other accounts
    - snapshot is explicitly identified as AWS Backup-managed
    - blocker checks are unavailable

Detection:
    - age >= threshold after blocker checks pass

Key rules:
    - This is a review-candidate rule, not a delete-safe rule.
    - Snapshot billing is incremental; cost must not be inferred from volumeSize.
    - Missing blocker visibility must cause skip, not optimism.

Blind spots:
    - business/DR intent is not known
    - AWS Backup management is not fully known unless explicitly integrated
    - deleting a snapshot might not reduce storage cost

APIs:
    - ec2:DescribeSnapshots
    - ec2:DescribeImages
    - ec2:DescribeSnapshotAttribute
"""
