aws.cloudwatch.logs.infinite_retention - Canonical Rule Specification

Intent
Detect CloudWatch Logs log groups in the current account and region that have no
retention policy configured and therefore retain log events indefinitely.

This is a read-only hygiene rule. It is not an idle-usage rule, not a deletion rule,
and not proof that changing retention is always appropriate.


1. AWS API grounding

This specification is anchored to official CloudWatch Logs API and user-guide behavior.

AWS facts relied on
- DescribeLogGroups returns log groups and includes, in the normal response objects:
  - logGroupName
  - creationTime
  - logGroupClass
  - retentionInDays
  - storedBytes
- retentionInDays is the configured retention period when a retention policy exists.
- PutRetentionPolicy sets retentionInDays to one of AWS's supported values.
- DeleteRetentionPolicy removes the retention policy, and AWS states:
  "Log events do not expire if they belong to log groups without a retention policy."
- CloudWatch Logs retention deletion is asynchronous:
  - log events can take up to 72 hours or longer to be physically deleted
  - once marked for deletion, they no longer add archival storage cost
  - marked-for-deletion data is not included in storedBytes
- DescribeLogGroups supports linked-account enumeration, but only when
  includeLinkedAccounts is explicitly enabled.
- If DescribeLogGroups is called with logGroupNamePattern, AWS returns only:
  - arn
  - creationTime
  - logGroupName
  Therefore a no-retention rule must NOT rely on logGroupNamePattern because
  retentionInDays and storedBytes are not returned in that response shape.
- logGroupClass can be:
  - STANDARD
  - INFREQUENT_ACCESS
  - DELIVERY
- DELIVERY class retention is service-managed, not user-configurable for this rule's
  purpose, and out of scope for this hygiene rule.

Rule-design consequence
- This rule is a deterministic configuration-hygiene detector for "no retention policy"
  on eligible log groups.
- This rule is NOT an idle detector and must not infer activity or inactivity from
  storedBytes.
- No-retention is a configuration fact and should be interpreted as such.


2. Scope

Included
- log groups returned by DescribeLogGroups in the current account and region
- logGroupClass in:
  - STANDARD
  - INFREQUENT_ACCESS
- log groups with retentionInDays absent or null

Excluded
- log groups with retentionInDays set
- log groups in DELIVERY class
- cross-account linked log groups unless the rule is explicitly extended to enable
  includeLinkedAccounts; no implicit cross-account coverage may be assumed
- malformed records without logGroupName


3. Canonical definitions

age_days
- Days since creationTime when creationTime is available.

min_age_days
- Noise-reduction heuristic for newly created groups.
- Recommended default: 7
- This is a product heuristic, not AWS behavior.
- Recommended enterprise posture: use this as context or risk input only, not
  as a default suppression rule.

stored_bytes
- The storedBytes value returned by DescribeLogGroups.
- This is a non-billing storage metric.

stored_gb
- stored_bytes / 1024^3

No-retention state
- retentionInDays is not present in the returned log group object.

Important rules
- No-retention state is a configuration fact, not a heuristic.
- storedBytes must not be used to infer "active" or "inactive".
- Missing creationTime must not suppress detection by itself.


4. Signal model

This rule uses three signal buckets.

A. EXCLUSION_RULES
These suppress findings.

1. retentionInDays is set
   -> SKIP

2. logGroupClass == DELIVERY
   -> SKIP

No default age-based suppression rule is part of this spec.
If product policy later enables new-group suppression, that must be specified
explicitly as a future spec revision.

B. DETECTION_SIGNAL
This is the only finding trigger.

1. Eligible log group has no retention policy configured
   - retentionInDays is not present in the returned log group object
   - logGroupClass is STANDARD or INFREQUENT_ACCESS

C. CONTEXTUAL_SIGNALS
These must not create or suppress findings directly unless explicitly listed above.

Contextual signals may only:
- affect risk
- appear in evidence/details

Contextual signals include:
- storedBytes / stored_gb
- creationTime / age_days
- logGroupClass
- deletionProtectionEnabled
- dataProtectionStatus
- kmsKeyId

Hard rules
- Contextual signals must not redefine no-retention state.
- storedBytes must not be treated as an activity signal.
- storedBytes is a non-billing storage metric only.


5. Evaluation order (mandatory)

All implementations must follow this order:
1. Parse and normalize log-group fields
2. Apply EXCLUSION_RULES
3. Detect no-retention state
4. Assign confidence
5. Assign risk
6. Build evidence/details


6. Path logic

This rule has one detection path only.

Path: no-retention
If:
- logGroupName exists
- logGroupClass is STANDARD or INFREQUENT_ACCESS
- retentionInDays is not present in the returned log group object

Then:
- MUST emit a finding

If any exclusion rule matches:
- MUST skip


7. Confidence model

Confidence measures certainty of the configuration problem, not certainty that
remediation is appropriate.

HIGH
- log group is eligible and retentionInDays is absent/null

Mandatory rule
- This rule should use HIGH confidence because the configuration state is directly
  observed from the AWS API.


8. Risk model

Risk measures business/operational urgency, not certainty.

Recommended default risk policy
- HIGH:
  - stored_gb >= 1.0
- MEDIUM:
  - stored_bytes > 0 and stored_gb < 1.0
- LOW:
  - stored_bytes == 0

Important notes
- These thresholds are product-policy choices, not AWS-defined thresholds.
- Infinite retention may still be intentional for compliance, audit, or security logs.
- storedBytes may be used only as a proxy for present storage exposure, not as a
  signal of activity, inactivity, or billing truth.


9. Cost model

Cost is informational only.

Mandatory rules
- Cost must not influence:
  - detection
  - confidence
- Cost may inform risk only if your product policy explicitly chooses to tie current
  stored size to urgency. If so, this must be stated clearly in the rule docs.
- The rule must not claim that storedBytes is billing data or a billing truth for
  future spend growth.

Allowed behavior
- Show an approximate storage-footprint-based storage-cost estimate from storedBytes
  using maintained AWS pricing references.

Required caveats
- pricing is region-dependent
- pricing source is outside the API itself
- storedBytes is not billing data
- storedBytes is a point-in-time storage metric, not a forecast
- this is storage-cost context only, not ingestion-cost context

Important AWS nuance
- For finite-retention groups, AWS excludes data already marked for deletion from
  storedBytes. This matters for explaining the field semantics.


10. Failure behavior

Required API
- logs:DescribeLogGroups
- If unavailable, the rule fails

Mandatory API usage rules
- Implementations MUST paginate DescribeLogGroups until nextToken is exhausted.
- A finding may only be emitted when retentionInDays is available on the actual
  DescribeLogGroups response objects used by the rule.
- If retentionInDays cannot be observed because the implementation used
  logGroupNamePattern or some other filtered response that omits it, the rule must not
  infer no-retention and must not emit findings from that incomplete data.

General rule
- This rule should rely on DescribeLogGroups only for its required detection path.
- Optional enrichment fields missing from an individual log group must not fail the scan.


11. Blind spots

Every emitted finding must disclose that the rule does not prove:
- whether infinite retention is intentional for compliance, audit, or security needs
- whether the log group is actively ingesting data
- future ingestion growth
- organizational retention policy intent
- cross-account coverage, unless linked-account scanning is explicitly enabled

The rule should also disclose:
- DELIVERY class is intentionally excluded because its retention is service-managed
- cross-account log groups are out of scope unless includeLinkedAccounts is explicitly
  enabled by spec


12. Evidence contract

Every finding must include:
- evaluation_path: no-retention
- log_group_name
- log_group_class
- retention state
- creationTime or null
- age_days or null
- stored_bytes or null
- stored_gb or null

Recommended evidence content
- "retentionInDays is not set (logs do not expire)"
- "log group age: X days" when creationTime is available
- "stored data: Y GB" when storedBytes is available

signals_not_checked is optional and should be included only when there are relevant
gaps or blind spots to disclose.

Suggested signals_not_checked content, as applicable:
1. intentional compliance/audit/security retention
2. recent ingestion activity
3. application-level usage context
4. future ingestion volume
5. cross-account linked log groups (if not scanned)

Details contract
- Missing fields must be explicit null values, not omitted.


13. Title and reason contract

Title
- CloudWatch log group with no retention policy

Reason
- Retention is not configured; log events do not expire

Hard rule
- Do not describe this as an idle or inactive log group.
- Do not describe zero storedBytes as "unused".


14. API and IAM contract

Required
- logs:DescribeLogGroups

Optional future enrichment (not required for core detection)
- logs:ListTagsForResource

API usage constraints
- Do not use logGroupNamePattern if the rule depends on retentionInDays or storedBytes.
- If cross-account support is added later, the spec must explicitly define
  includeLinkedAccounts behavior.
- No implicit cross-account coverage assumption is allowed.


15. Acceptance scenarios

Must emit
1. STANDARD log group, retentionInDays absent
2. INFREQUENT_ACCESS log group, retentionInDays absent
3. no-retention log group with storedBytes == 0
4. no-retention log group with storedBytes > 0

Must skip
1. retentionInDays set to any valid AWS retention value
2. DELIVERY class log group, even if retentionInDays is absent
3. malformed record without logGroupName

Must not happen
1. DELIVERY log groups are labeled "infinite retention"
2. storedBytes is treated as proof of activity or inactivity
3. logGroupNamePattern-only responses are used to infer no-retention
4. a missing creationTime suppresses a finding by itself
5. incomplete pagination causes silent coverage loss


16. Short in-file contract

Suggested header for cloudwatch_logs_no_retention.py:

"""
Rule: aws.cloudwatch.logs.infinite_retention

Intent:
    Detect eligible CloudWatch log groups with no retention policy configured.

Exclusions:
    - retentionInDays is set
    - DELIVERY class log groups

Detection:
    - retentionInDays absent/null on STANDARD or INFREQUENT_ACCESS log groups

Key rules:
    - This is a hygiene/configuration rule, not an idle rule.
    - Missing retention is a direct AWS-observed configuration fact.
    - storedBytes must not be used as an activity signal.
    - storedBytes is a non-billing storage metric.
    - DELIVERY class must be excluded because its retention is service-managed.

Blind spots:
    - intent for compliance/audit/security retention is not known
    - ingestion/activity is not checked
    - future log growth is not known

API:
    - logs:DescribeLogGroups
"""
